> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Signal-K marine data, subdomain routing docs, a self-contained landing page, persistence testing, and security hardening to the SeaTurtleOS service stack.

**Architecture:** 7 services on a shared Docker network (`seaturtle`) with bind mounts to `./data/`. A `mosquitto-init` container generates auth credentials at startup. Node-RED computes its own bcrypt hash from the plaintext env var. A tiny `nginx:alpine` landing page shows service links and default credentials. SSL is deferred to Phase 4 (Pi image).

**Tech Stack:** Docker Compose, Eclipse Mosquitto 2, Node-RED 4.1.x, Signal K v2.24.x, Grafana 11.x, Prometheus v3.4.x, Nginx Proxy Manager 2.14.x, Portainer CE 2.27.x, nginx:alpine (landing page).

**Phase Order:** 3 (Signal-K) → 2 (NPM routes + landing page) → 6 (Security) → 5 (Persistence) → commit everything.

- [ ] **Step 3: Add mosquitto-init service to compose**

Add before the `mosquitto` service block:

```yaml
  # ── MQTT Auth Init ──────────────────────────────────────────────
  # Generates the Mosquitto password file on first run, then exits.
  # Re-running is safe — overwrites the password file with current env values.
  mosquitto-init:
    image: eclipse-mosquitto:2
    container_name: seaturtle-mosquitto-init
    entrypoint: >
      sh -c '
        touch /mosquitto/config/passwd &&
        mosquitto_passwd -b /mosquitto/config/passwd
        "$${MQTT_USER}" "$${MQTT_PASS}" &&
        echo "mosquitto-init: password file written for user $${MQTT_USER}"
      '
    environment:
      - MQTT_USER=${SEATURTLE_MQTT_USER:-seaturtle}
      - MQTT_PASS=${SEATURTLE_INITIAL_PASSWORD:-changeseaturtle}
    volumes:
      - ./data/mosquitto/config:/mosquitto/config
    networks:
      - seaturtle
```

**Files:**

```markdown
# ADR 0002: Subdomain Routing Scheme

## Status

Accepted

## Date

2026-04-05

## Context

SeaTurtleOS runs multiple web services that need to be accessible through the
Nginx Proxy Manager reverse proxy. Two routing strategies were considered:

1. **Path-based** — e.g., `http://seaturtle.local/grafana`, `http://seaturtle.local/nodered`
2. **Subdomain-based** — e.g., `http://grafana.seaturtle.local`, `http://nodered.seaturtle.local`

### Path-based issues

Several services (Grafana, Node-RED, Portainer, Signal K) assume they are served
at the root path (`/`). Path-based routing requires each application to be
reconfigured with a sub-path prefix, and many generate hardcoded absolute URLs
to `/`, breaking navigation, WebSocket connections, and asset loading.

### Subdomain advantages

Each service gets its own origin. No sub-path rewriting needed. Applications
work unmodified. A single wildcard SSL certificate (`*.seaturtle.local`) covers
all services.

### SSL on .local domains

`.local` domains cannot use Let's Encrypt (no public DNS validation). Options:

- **Self-signed wildcard CA**: Generate a root CA certificate, issue a
  `*.seaturtle.local` wildcard cert. Users install the CA cert once on their
  devices. NPM serves the wildcard cert for all proxy hosts.
- **No SSL**: Services are HTTP-only on the local network. Acceptable for
  development and isolated boat networks with no untrusted devices.

SSL certificate generation is deferred to Phase 4 (Pi image building) where the
CA cert and wildcard cert will be baked into the image and NPM's SQLite database.

## Decision

Use **subdomain-based routing** with the `*.seaturtle.local` domain pattern.

### Subdomain Map

| Subdomain | Upstream | Port |
|-----------|----------|------|
| `seaturtle.local` | landing page | 8080 |
| `signalk.seaturtle.local` | signalk | 3000 |
| `nodered.seaturtle.local` | nodered | 1880 |
| `grafana.seaturtle.local` | grafana | 3000 |
| `portainer.seaturtle.local` | portainer | 9000 |
| `prometheus.seaturtle.local` | prometheus | 9090 |
| `npm.seaturtle.local` | nginx-proxy-manager | 81 |

### DNS Resolution

On the Pi image, a lightweight DNS resolver (dnsmasq or systemd-resolved) will
resolve `*.seaturtle.local` to the Pi's IP address. For development on macOS,
add entries to `/etc/hosts` or use dnsmasq via Homebrew.

## Rationale

- Applications work unmodified at root path — no sub-path configuration needed
- Single wildcard cert covers all services
- Clean separation of origins (no cookie/localStorage collisions)
- NPM GUI makes subdomain proxy hosts trivial to create

## Consequences

- Requires DNS configuration (dnsmasq on Pi, /etc/hosts for dev)
- Users must install a CA certificate for HTTPS (deferred to Phase 4)
- Adding a new service requires both a Compose entry and an NPM proxy host
```

# ADR 0003: Signal K as Marine Data Hub

## Status

Accepted

## Context

SeaTurtleOS needs to ingest, normalize, and distribute marine instrument data
from NMEA 2000 and NMEA 0183 networks. Signal K is the open-source standard

### Signal K Server

- **Image**: `signalk/signalk-server` (also at `cr.signalk.io/signalk/signalk-server`)

- The MQTT gateway plugin enables loose coupling with the rest of the stack
- Plugin ecosystem covers AIS, anchor watch, weather, and more
